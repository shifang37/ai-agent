# ai-agent 两阶段检索评测报告（向量召回 + Rerank 精排）

项目：AI 智能体应用平台（项目文件夹：`ai-agent`）
日期：2026-07-13

## 评测设置

- **知识库**：`backend/src/main/resources/document/` 三份恋爱知识文档（单身/恋爱/已婚篇），
  经 `MarkdownDocumentReader` 分块为 15 个知识块，每块含一个唯一课程名（作为命中标记）。
- **评测集**：`backend/src/test/resources/rag-eval-dataset.json`，45 条口语化改写问句
  （每个知识块 3 条，刻意与原文措辞不同，且包含多组语义相近的干扰主题）。
- **判定标准**：检索返回的 top-N 文档文本包含目标知识块的课程名即命中。
- **运行方式**：`cd backend && ./mvnw test -Dtest=RetrievalEvalTest`
- Embedding（text-embedding）与 Rerank（gte-rerank-v2）均真实调用 DashScope API，
  本轮 43 次 rerank 调用全部成功（2 条查询候选数 ≤3 跳过精排）。

## 三组对照结果（45 条查询）

| 方案 | Hit Rate@1 | Hit Rate@3 |
|---|---|---|
| A 单阶段向量检索（课程原版：topK=3，阈值 0.5） | 39/45 = **86.7%** | 39/45 = **86.7%** |
| B 消融组：仅放宽召回（topK=15，阈值 0.3，取向量序前 3） | 44/45 = **97.8%** | 45/45 = **100%** |
| C 两阶段：放宽召回 + gte-rerank-v2 精排 top3 | 42/45 = **93.3%** | 45/45 = **100%** |

**最终交付效果（A → C）：Hit@3 86.7% → 100%（+13.3pp），Hit@1 86.7% → 93.3%（+6.6pp）。**

## 关键发现（面试可讲的完整故事）

### 1. 基线的瓶颈在召回而非排序（消融实验定位）

基线 6 条未命中的问句（如「网恋聊天怎么聊才不会把天聊死？」「婚后天天围着家转，感觉
失去了自我怎么办？」）都是口语化改写幅度大的难例——其与正确文档的向量相似度低于 0.5，
被**相似度阈值直接过滤**，属于召回缺失而非排序错误。消融组 B 证明：仅把阈值放宽到 0.3、
topK 放宽到 15，Hit@3 即达 100%。

两阶段架构的价值正在于此：**放宽召回提升覆盖率，靠精排阶段控制最终送入上下文的数量与
质量**，从而化解「召回率 vs 上下文长度」的矛盾。单阶段检索若直接放宽阈值，只能靠调大
topK 塞更多文档进上下文（token 成本线性上涨）。

### 2. SDK 默认 rerank 模型已下线，降级逻辑掩盖了故障

首轮评测中 rerank 调用全部返回 `403 AccessDenied`，但因实现了「精排失败自动降级为向量
top3」，两阶段成绩看起来依然提升——**假提升**。通过对照组比对（成绩与 rerank 是否生效
无关）才暴露问题，直连 API 逐一排查后定位根因：spring-ai-alibaba 1.0.0-M6.1 的
`DashScopeRerankOptions` 默认模型名 `gte-rerank` 已在 DashScope 下线，需显式指定
`gte-rerank-v2`（已在 `RerankDocumentRetriever` 中固化）。

教训：优雅降级必须配合监控告警，否则会把故障静默吞掉；评测必须设消融对照组，否则
归因错误。

### 3. 小语料上 rerank 的排序增益有限

15 块语料、每域仅 5 个候选时，embedding 排序已足够强：C 组 Hit@1（93.3%）反而略低于
B 组（97.8%），gte-rerank-v2 在 2 条近义问句上把 top1 排错（交叉编码器对短文档近义对
的打分接近，存在翻转）。rerank 的排序价值需要在更大规模、候选更密集的语料上才能体现；
本项目中它的现实作用是**为放宽召回兜底、保证送入上下文的文档数量恒定为 3**。
